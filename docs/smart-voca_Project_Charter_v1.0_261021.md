## 2. 배경 및 목적

### 2.1 배경
- `[가정]` 단어 암기는 반복 학습이 핵심이지만, 복습 시점을 수동으로 관리하기 어렵다.
- `[가정]` 기존 단어장 방식은 학습 진척도와 복습 필요 여부를 알려주지 않는다.

### 2.2 목적
- 단어별 기억 상태를 기록하고, 복습 시점을 자동으로 계산한다.
- 학습자가 매일 해야 할 학습량을 한눈에 보게 한다.

### 2.3 기대 효과
- `[가정]` 복습 누락을 줄여 단어 장기 기억률을 높인다.
- 학습 기록을 통해 진척도를 객관적으로 확인한다.

## 3. 비즈니스 요구사항 (BRD)

| ID | 요구사항 | 우선순위 | 비고 |
|----|----------|----------|------|
| BR-01 | 학습자가 단어장을 만들고 단어를 추가·수정·삭제할 수 있어야 한다 | 상 | |
| BR-02 | 단어별 학습 결과에 따라 다음 복습 시점이 자동으로 정해져야 한다 | 상 | 간격 반복(Spaced Repetition) 방식 `[가정]` |
| BR-03 | 오늘 복습해야 할 단어 목록을 보여줘야 한다 | 상 | |
| BR-04 | 학습 기록(정답률, 학습 일수)을 확인할 수 있어야 한다 | 중 | |
| BR-05 | 학습 데이터는 학습자별로 분리되어야 한다 | 중 | 로그인 방식 미정 (§ 9) |
| BR-06 | 단어 발음·예문 등 부가 정보를 제공할 수 있어야 한다 | 하 | 데이터 출처 미정 |

## 4. 시스템 범위 (System Scope)

### 4.1 포함 범위 (In Scope) — MVP
- 단어장 CRUD (생성, 조회, 수정, 삭제)
- 단어 CRUD (단어, 뜻, 예문)
- 학습 세션: 단어 카드 뒤집기, 정답/오답 입력
- 복습 스케줄 계산 (간격 반복 알고리즘)
- 오늘의 복습 목록 조회
- 기본 학습 통계 (학습 일수, 정답률)

### 4.2 제외 범위 (Out of Scope) — MVP 이후 검토
- 음성 인식·발음 평가
- 외부 사전 API 연동 `[가정]`
- 소셜 기능 (친구 공유, 랭킹)
- 모바일 네이티브 앱 `[가정]` 웹 기반으로 시작

### 4.3 주요 기능 후보 (추후 Requirement Spec에서 ID 부여)
| 후보 기능 | 연결 BR |
|-----------|---------|
| 단어장 관리 | BR-01 |
| 단어 관리 | BR-01 |
| 학습 세션 | BR-02 |
| 복습 스케줄러 | BR-02, BR-03 |
| 학습 통계 | BR-04 |
| 사용자 구분 | BR-05 |

## 5. 가정 및 제약

### 5.1 가정
- `[가정]` 학습자는 1인 사용을 기본으로 하며, 초기에는 학습자 한 명의 데이터만 다룬다.
- `[가정]` 단어 데이터는 사용자가 직접 입력한다 (외부 데이터 자동 수집 없음).
- `[가정]` 실행 환경은 로컬 개발 환경이며, 배포 방식은 MVP 이후 정한다.

### 5.2 제약
- 개발 기간·인력: 미정 (§ 6 일정 참조)
- 개인정보: 학습자 이름·연락처 등을 수집하지 않는 방향 `[가정]` (CLAUDE.md 코드 작성 규칙 6 준수)
- 비밀정보(API 키, DB 접속정보)는 코드에 쓰지 않고 `.env`로 관리 (CLAUDE.md 코드 작성 규칙 5 준수)

## 9. 확인 필요 질문

확정을 위해 아래 항목에 대한 답이 필요하다.

1. **서비스 형태** — ✅ **결정: 웹 기반 (2026-11-11)**
   - 배경: 단어장·복습 목록은 브라우저로 충분히 다룰 수 있고, 초기 1인 사용을 가정함.
   - 대안: 모바일 앱(Android/iOS), 데스크톱 앱, 웹 후 모바일 확장
   - 결정 근거: 설치 없이 바로 쓸 수 있어 MVP 개발 부담이 가장 적음. 모바일 앱은 MVP 이후 검토(§4.2).
   - 되돌림 가능성: 있음. 모바일 요구가 생기면 ADR로 재검토.
2. **대상 사용자**: 누가 쓰는가? (학생, 일반인, 외국어 학습자 등)
3. **학습 언어와 단어 형식**: 어떤 언어 쌍인가? 단어 외 예문·발음도 다루는가?
4. **복습 방식**: 간격 반복 알고리즘을 직접 구현하는가, 기존 방식을 쓰는가?
5. **사용자 구분**: 로그인이 필요한가, 아니면 단일 사용자로 충분한가?
6. **기술 스택** — ✅ **결정: Python 3 + FastAPI + SQLAlchemy + Jinja2/HTMX + SQLite (2026-11-11)**
   - 상세: `docs/smart-voca_Decision_Records_v1.0_261111.md`
   - 근거: 1인·로컬 사용 가정에 맞는 단순 구성, CLAUDE.md 규칙과 일치, 간격 반복 계산 테스트 용이
   - 재검토 조건: 로그인 필요(§9-5) 확정 시 Django 검토
7. **기간과 인력**: 마감일과 참여 인원은?
8. **범위 확정**: § 4.1 MVP 범위에 빠지거나 추가할 기능이 있는가?
