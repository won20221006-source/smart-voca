## 4. 추천안

**백엔드 Python + FastAPI, 프론트는 서버 렌더링(Jinja2) + HTMX 또는 최소 JS, DB는 SQLite.**

### 근거
1. 1인 사용·로컬 실행 가정이므로 DB는 SQLite가 가장 단순하다. 파일 하나로 백업과 이동이 쉽다.
2. CLAUDE.md 규칙(Python 헤더, 스크립트 위치, `.env` 환경변수)과 맞는다.
3. 웹 MVP 기능(CRUD, 오늘의 복습 목록, 통계)은 FastAPI로 짧게 구현할 수 있다.
4. 간격 반복 계산과 통계는 Python에서 테스트하기 쉽다.

### 대안이 더 맞는 경우
- **로그인이 필요하고 관리자 화면이 필요하면 → C. Django**. 인증과 admin이 기본 제공된다.
- **SPA(화면 전환이 많은 UI)를 원하면 → B. Node.js + TypeScript + React**. 프론트 경험이 중요한 경우에 적합하다.
- **동시 사용자가 많아질 것이 확실하면 → DB를 PostgreSQL로 변경**. 초기에는 필요 없다.

### 되돌림 가능성
- 중간 수준. 백엔드 프레임워크를 바꾸면 라우팅과 템플릿을 다시 작성해야 한다. DB 스키마는 SQLAlchemy 같은 ORM을 쓰면 SQLite에서 PostgreSQL로 옮기기 쉽다.

## 5. 확인 필요 (승인 전)

1. 위 추천안(FastAPI + Jinja2/HTMX + SQLite)으로 확정할지
2. 대안(Django, Node.js + React, PostgreSQL) 중 선택할지
3. 로그인이 MVP에 필요한지 (기획서 §9-5). 필요하면 Django 쪽 검토가 더 맞다.

## 6. 결정 기록 — MVP 세부 방침 (2026-11-18, 사용자 위임)

사용자가 "알아서 진행"을 요청하여 아래 미결 사항을 MVP 기준으로 정했다. 되돌릴 가능성이 있으므로 근거를 함께 남긴다.

### 6-1. 복습 간격 방식 (기획서 §9-4, 요구사항 REQ-016~018)
- **배경**: 간격 반복 알고리즘을 직접 구현할지, 고정 간격으로 시작할지 미정이었다.
- **대안**: (a) 고정 간격 1→3→7→14→30일, 오답 시 1일 (b) SM-2 류 간격 반복 알고리즘 (c) 외부 라이브러리
- **결정**: (a) 고정 간격. 계산기는 `ReviewScheduler` 인터페이스 뒤에 두어 교체 가능하게 한다 (`src/core/scheduler.py`).
- **근거**: 1인 MVP에서 기능 검증이 우선이다. 간격 값은 `src/core/config.py` 상수로 분리했다. 간격 반복 방식이 필요해지면 인터페이스 구현체만 추가하면 된다.

### 6-2. 로그인 (기획서 §9-5, REQ-025~026)
- **결정**: MVP는 로그인 없음. 단일 사용자로 동작한다.
- **근거**: 1인 사용 가정과 일치한다. 로그인이 도입되면 §0 미결 사항에 따라 Django 대안을 재검토한다.

### 6-3. 학습 방식 (REQ-013)
- **결정**: 카드 뒷면을 펼쳐 본 뒤 정답/오답을 직접 선택한다. 뜻 직접 입력 방식은 쓰지 않는다.
- **근거**: 구현이 단순하고 기록 규칙이 명확하다. 입력 채점은 후속 과제로 둔다.

### 6-4. 새 단어의 첫 복습일 (REQ-019 가정)
- **결정**: 추가한 날 바로 복습 대상이다.
- **근거**: 추가 직후 한 번은 확인하도록 하기 위함이다. 바꾸려면 `create_initial_state`만 수정하면 된다.

### 6-5. 웹 화면 기술
- **결정**: HTMX 없이 일반 HTML 폼과 리다이렉트로 구현한다. 삭제 확인만 최소 JS(`confirm`)를 쓴다.
- **근거**: 기술 스택 추천안의 "HTMX 또는 최소 JS" 범위 안에서 가장 단순한 선택이다.
